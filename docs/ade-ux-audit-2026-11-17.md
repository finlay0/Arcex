# Arcex ADE UX audit

November 17, 2026 · Windows development build · `feat/ade` at `222a1a5`

Arcex has a clear workspace structure. Projects and threads sit on the left, the conversation gets the centre, and files, changes and preview live beside it. The dark default, local fonts and art on the empty screens give the interface a consistent visual identity. The product can support a supervised demo with a preconfigured agent. I would hold an unsupervised beta until a first-time user can connect an agent, reliably stop it, and recover their work after something fails.

The biggest product gap appears on the second visit. A user can find earlier conversations, a project goal and the current working-tree changes. There is no durable project-level view of what got done, what was verified, what is blocked or where to resume. That view would give the user a reason to return to Arcex when several agents have worked on the same project.

## Scope and evidence

The ADE is the product under audit. The retained Radar, Vault and MCP platform received a limited check where it touches the ADE. Findings come from the current Electron, React and engine source, plus an isolated Windows engine run with synthetic folders and a local ACP test agent. Desktop interaction and visual checks were stopped at the user's request. Layout and keyboard findings are based on source. Live provider sign-in, provider billing, screen readers, Windows scaling and the public web UX were outside this run.

The IDE build, engine typecheck, repository check with 31 passing platform tests, and platform smoke against isolated local D1 all passed. The platform checks do not exercise the desktop flows below.

Adding an ordinary folder initialized Git in the fixture without explaining the change first. ## Conversation, control and recovery

| Priority | Finding | What should change |
| --- | --- | --- |
| Critical | **Stop can return success and still run the prompt.** With a deliberately slow ACP handshake, the Stop request returned OK, the agent never received cancellation, and it subsequently wrote a file. During startup the cancel handler has no session to notify. ACP initialization also lacks an explicit timeout. [Startup and cancellation](../apps/engine/src/engine.ts#L227) · [Cancel handler](../apps/engine/src/engine.ts#L446) | Carry cancellation across session startup. Show “Stopping…” until the outcome is known, distinguish “Stopped” from “Finished,” and explain that already-completed edits may remain. |
| High | **The model label can disagree with the model that ran.** The fixture rejected a stale model and continued using its baseline model while thread state still displayed the rejected selection. In an existing session, choosing Default also skips applying a model change. [Startup model handling](../apps/engine/src/engine.ts#L215) · [Model update](../apps/engine/src/engine.ts#L412) | Show the agent-confirmed model. If it rejects a choice, preserve the prior confirmed value or ask the user to approve the fallback before sending. |
| High | **A failed turn can look finished from elsewhere.** The fixture rejected a turn and the engine saved the error in the transcript, then returned the thread to idle. Recent activity gives idle threads a check icon. The background notification can say “Finished” after the same transition. The turn finalizer also changes remaining running steps to done. [Turn finalization](../apps/engine/src/engine.ts#L227) · [Notifications](../apps/ide/src/App.tsx#L158) · [Recent activity](../apps/ide/src/views.tsx#L450) | Persist the turn outcome and use it consistently in the transcript, recent activity, sidebar and alerts. Provide a retry action beside the failed message. |
| High | **Unsent text and connection recovery are fragile.** The composer clears before the RPC is acknowledged. Its draft is component state, so going through agent setup, opening another thread or reloading can lose it. A closed socket replaces the workspace with “Close and reopen the app.” Startup waits for the engine before creating a window. [Composer](../apps/ide/src/views.tsx#L245) · [View switching](../apps/ide/src/App.tsx#L399) · [Connection handling](../apps/ide/src/store.ts#L28) · [Desktop startup](../apps/desktop/src/main.cjs#L28) | Store drafts by project and thread, clear them after acknowledgement, and surface engine reconnect or restart within the window. On restart, identify turns interrupted mid-run. |
| High | **Approval behaviour remains unverified with the supported providers.** The app has an approval card for requests the provider sends. The current integration leaves provider modes to the CLI, and the project notes record no exercise of the ask-first path. Users cannot tell from the workspace whether the active agent will request approval before writing or running commands. [Permission handler](../apps/engine/src/engine.ts#L165) · [Approval UI](../apps/ide/src/views.tsx#L88) · [Build notes](ade-plan.md) | Surface each provider's active approval behaviour. Verify allow, decline, stop while waiting, and agent exit while waiting for the Windows providers supported at launch. |

## Projects, review and preview

| Priority | Finding | What should change |
| --- | --- | --- |
| High | **Changes answers a narrower question than its copy suggests.** It lists uncommitted Git changes across the project. A successful commit can clear the list, unrelated work can appear beside an agent's edits, and Git failures can look like an empty list. The fixture also showed a Unicode filename listed as an escaped path and opening as a blank diff. “Nothing has changed since the last save point” suggests a checkpoint system that the current build lacks. [Git changes](../apps/engine/src/git.ts#L8) · [Changes panel](../apps/ide/src/views.tsx#L530) | Label and qualify the current view accurately. Preserve path names, distinguish failure from clean status, and add a durable per-turn review that identifies each agent's edits. |
| High | **The Browser can signal readiness before the app loads.** The green indicator is conditional on a saved URL. A stale localhost address or a page that blocks framing can produce a blank or error frame without a useful explanation from Arcex. Agent-mentioned URLs are suggestions drawn from historical messages. [URL discovery](../apps/ide/src/views.tsx#L392) · [Browser panel](../apps/ide/src/views.tsx#L578) | Separate address saved, loading, reachable and unavailable. Put retry and “Open in browser” next to the failed preview. Preserve suggested addresses so users can switch between them after setting an initial URL. |
| Medium | **Project navigation mostly organizes threads.** The project row expands the tree. Goal editing and project removal live in Settings. Thread search searches active titles only, and archived threads are elsewhere. On reopen the selected project is remembered while the app starts at a fresh thread. [Sidebar](../apps/ide/src/App.tsx#L251) · [Settings](../apps/ide/src/Settings.tsx#L176) | Give each project a home with its goal, work needing attention, and a clear resume action. Make archive discoverable from the project, and explain the scope of thread search. |
| Medium | **The file tree is a good orientation aid with a limited review path.** Folder rows expand, but file rows are static. A user who sees a file has to find it through Changes or leave the workspace to inspect its contents. Removal confirmations focus on the action and give limited context about conversation history versus files on disk. [File tree](../apps/ide/src/views.tsx#L480) · [Project settings](../apps/ide/src/Settings.tsx#L183) | Add read-only file inspection or an explicit open action. Describe deletion consequences at confirmation and make archive the obvious reversible option. |

## Interaction design and accessibility

- **High · Panel widths compete with the conversation.** At the 1,100 px window minimum, the 292 px sidebar and 506 px Browser panel leave about 302 px for the conversation before its padding. The new-thread model picker is 560 px wide and opens downward inside a scrolling hero. This creates a clipping risk at minimum size and under scaling. Let the user resize the panel or switch it into a wider view, and position menus within the visible window. [Window limits](../apps/desktop/src/main.cjs#L31) · [Layout and picker styles](../apps/ide/src/ui.css#L229)
- **High · Important actions need a complete keyboard path.** Thread rows simulate buttons with Enter only and contain a second button. The generic action menu uses menu roles without focus handling, arrow navigation or Escape dismissal. Details and Browser declare tab roles without the usual tab keyboard behaviour. Composer textareas rely on placeholders for their names. Use native controls where possible and check focus on opening, closing and switching screens. [Thread rows and menu](../apps/ide/src/App.tsx#L22) · [Composer](../apps/ide/src/views.tsx#L275) · [Panel tabs](../apps/ide/src/views.tsx#L410)
- **Medium · Improve legibility before adding more visual detail.** The dark composer placeholder measures 3.86:1 against its surface, and the sidebar shortcut text measures 2.24:1. Several icon-only controls rely on accessible names without a visible hover label. The continuously animated outline is strongest on the focused composer, including the first screen. Keep the existing reduced-motion handling and raise contrast on actionable text, make structural controls discoverable, and use steady focus treatment. [Tokens and base focus styles](../apps/ide/src/ui.css#L5) · [Composer treatment](../apps/ide/src/ui.css#L203)
- **Medium · Keep common error and loading states in place.** The initial renderer can be empty while bootstrapping, with no inline retry on state load failure. Some project calls leave “Loading…” visible and use a brief toast for the error. The panel should tell the user whether the query failed, the folder is empty, or the engine is still connecting. [Startup rendering](../apps/ide/src/App.tsx#L210) · [File loading](../apps/ide/src/views.tsx#L480)

## Toolbox and the retained platform

The Toolbox is an approachable way to bring a tool into a conversation. The action queues a prompt that invites the agent to proceed after explaining the tool, with no separate review step. On a clean workspace the user lands on project creation first. Make the action state what will happen next and keep the selected tool visible through project selection. The optional Research Library setting explains when requests go to arcex.dev and starts off. It is read when an ACP session opens, so changing it can leave already-open sessions with their original capabilities. Tell the user when the setting takes effect. The web repository still uses “Insider” in account and checkout copy while the current product decision is “Pro.” That is a source finding about the retained platform. ## Release sequence

1. **Make the first turn work on a clean Windows account.** Start from an idea and open a folder, establish the correct provider, send a prompt, and return from setup with the draft intact.
2. **Make execution and recovery trustworthy.** Verify Stop at startup, mid-turn and while awaiting approval. Verify an unavailable model, provider failure and engine exit each leave a truthful status and a way to resume.
3. **Make the work reviewable.** See what changed in each turn, distinguish existing edits, and open the running app or understand why preview failed. Acceptance should include two agents touching the same project and one committing its work.
4. **Prove the reason to reopen Arcex.** Close after two agents have worked, reopen, and answer within a minute what changed, which result is backed by evidence, what is unresolved, and what to do next. Start with saved turn outcomes, changed files and a resume action. The existing plan holds background recaps pending a decision, so this checkpoint can be tested with direct evidence from the engine.
5. **Check keyboard, scaling and packaging on the release build.** Walk the core flow with keyboard only and at the minimum window size under Windows display scaling. Confirm the installer and update path on a clean machine.
